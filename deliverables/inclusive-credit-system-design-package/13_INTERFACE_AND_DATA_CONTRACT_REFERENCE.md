# 13. Interface, API, and Data Contract Reference

## 13.1 Contract philosophy

The platform sits between a lender workflow and a versioned model. Its interfaces must do more than move JSON. They must preserve the identity of the model, feature schema, decision policy, explanation method, and audit transaction that produced each result. This section documents the current principal contract and the additional production properties required for reliable integration.

The principal base paths are:

```text
GET  /health
GET  /docs
GET  /redoc

GET  /v1/models/current
GET  /v1/features/contract
POST /v1/score
POST /v1/explain
POST /v1/portfolio/analyze
POST /v1/audit/fairness
POST /v1/audit/events
GET  /v1/audit/events
GET  /v1/governance/summary
```

`/docs` and `/redoc` are generated by FastAPI. They are enabled in the reference application. Production exposure should be decided per environment and protected when schema detail is sensitive.

## 13.2 Common request controls

All `/v1` routes share the API-key dependency. The current behavior is:

```python
if settings.api_key is None:
    return
if x_api_key != settings.api_key:
    raise HTTPException(
        status_code=401,
        detail="Unauthorized",
    )
```

Production identity must replace this shared-secret comparison with authenticated client identity and tenant-scoped authorization. Recommended claims include institution, environment, client application, product, operation, role, key identifier, and credential-expiration state. Authentication and authorization events should be logged without storing credentials.

Common headers for the production contract:

```http
Authorization: Bearer <client credential token>
Idempotency-Key: <opaque caller-generated key>
X-Correlation-ID: <optional caller correlation value>
Content-Type: application/json
Accept: application/json
```

The current frontend uses `X-API-Key` when `VITE_API_KEY` is present. Putting a long-lived lender credential into a browser build is not an acceptable production design. The browser should call a lender-controlled backend or a secure session layer.

## 13.3 Pseudonymous application reference

The principal request models inherit an `application_id` field with a length of 3 to 128 characters. The custom validator trims whitespace, applies this character rule, and rejects common direct-identifier patterns:

```regex
^[A-Za-z0-9][A-Za-z0-9_.:-]{2,127}$
```

Accepted examples:

```text
app_01HX9Z7Y
loan-session:1842
case.external-002
```

Rejected classes include email-shaped strings, common telephone-shaped strings, government-ID patterns, values containing spaces, values outside the length boundary, and values containing unapproved characters. The caller remains responsible for creating an opaque reference that does not encode a name, account, telephone number, government identifier, or other direct identifier.

## 13.4 Health contract

**Operation:** `GET /health`
**Authentication:** none in current code
**Response model:** untyped dictionary

```json
{
  "status": "ok"
}
```

The current response is liveness only. A production public health response should remain minimal. An authenticated readiness response may include bounded dependency states and the active model version, but should not reveal filesystem paths or secrets.

## 13.5 Current-model contract

**Operation:** `GET /v1/models/current`
**Response:** current pointer and matching registry entry

```json
{
  "current": {
    "name": "sklearn_logreg_baseline",
    "version": "0.0.1"
  },
  "entry": {
    "name": "sklearn_logreg_baseline",
    "version": "0.0.1",
    "artifact_path": "artifacts/models/baseline.joblib",
    "created_at": "registry-generated value",
    "feature_schema_hash": "a991402390c9a9aa",
    "decision_threshold": 0.5,
    "metrics": {
      "roc_auc": 0.56588288
    },
    "fairness": {},
    "notes": "Synthetic/demo baseline training run."
```

The local artifact path is useful for reproduction but should not be published to ordinary production clients. A production response should expose a public model identifier, version, policy version, schema version, and status while keeping storage location and internal approval evidence behind governance authorization.

## 13.7 Score request

The current Pydantic model is conceptually:

```python
class ScoreRequest(PseudonymousApplicationModel):
    features: dict[str, float]
    sensitive_attributes: dict[str, str] | None = None
    request_id: str | None = None
```

`features` is a flexible dictionary at the HTTP schema layer. The core contract performs name validation. `sensitive_attributes` is also a flexible map of strings and is not used by the model vector. `request_id` is optional and not length- or character-constrained by a custom validator.

The request model does not set Pydantic `extra="forbid"`. Unknown top-level fields may therefore be ignored rather than rejected depending on the model configuration. The feature dictionary itself does reject unknown names in the core contract.

Production request proposal:

```json
{
  "application_id": "opaque-lender-reference",
  "feature_contract_version": "alt-credit-v1",
  "decision_policy_version": "community-product-v1",
  "features": {
    "rent_on_time_rate_12m": 0.96,
    "utility_on_time_rate_12m": 0.93,
    "avg_monthly_income_6m": 4500,
    "cashflow_volatility_6m": 0.12,
    "avg_daily_balance_6m": 1800,
    "nsf_events_12m": 0,
    "overdraft_events_12m": 0
  },
  "feature_provenance": {
    "snapshot_id": "snapshot-opaque-reference",
    "provider_manifest_id": "manifest-opaque-reference"
  }
}
```

Sensitive monitoring attributes should use a separate restricted ingestion operation or tokenized monitoring stream rather than the general score request in a production architecture.

## 13.8 Score response

Current response model:

```python
class ScoreResponse(BaseModel):
    application_id: str
    request_id: str
    model_name: str
    model_version: str
    feature_schema_hash: str
    score: float
    decision: str
    decision_threshold: float
    reason_codes: list[str]
    created_at: str
    extra: dict[str, Any]
```

The response does not constrain `decision` to an enumeration or constrain score to `[0, 1]` at the schema level, although the logistic model produces a probability. Production fields should include decision-policy version, reason-dictionary version, explanation status, audit event ID, review requirements, result expiration or staleness policy, and idempotency reference.

Example current response shape:

```json
{
  "application_id": "app_example_001",
  "request_id": "request-opaque-reference",
  "model_name": "sklearn_logreg_baseline",
  "model_version": "0.0.1",
  "feature_schema_hash": "a991402390c9a9aa",
  "score": 0.64,
  "decision": "approve",
  "decision_threshold": 0.5,
  "reason_codes": [
    "RC_HIGH_CASHFLOW_VOL"
  ],
  "created_at": "service-generated value",
  "extra": {}
}
```

The example value is illustrative. It is not a reproduced output from the evidence run.

## 13.10 Fairness request and response

Request row:

```python
class FairnessRow(BaseModel):
    protected_group: str = Field(min_length=1)
    y_true: int = Field(ge=0, le=1)
    y_pred: int = Field(ge=0, le=1)
```

Example batch:

```json
{
  "rows": [
    {"protected_group": "group_a", "y_true": 1, "y_pred": 1},
    {"protected_group": "group_a", "y_true": 0, "y_pred": 1},
    {"protected_group": "group_b", "y_true": 1, "y_pred": 0},
    {"protected_group": "group_b", "y_true": 1, "y_pred": 1}
  ],
  "positive_label": 1
}
```

Response:

```json
{
  "groups": ["group_a", "group_b"],
  "counts_by_group": {"group_a": 2, "group_b": 2},
  "demographic_parity_difference": 0.5,
  "equal_opportunity_difference": 0.5,
  "selection_rate_by_group": {"group_a": 1.0, "group_b": 0.5},
  "tpr_by_group": {"group_a": 1.0, "group_b": 0.5}
}
```

This is the batch used by the end-to-end test, and it explains why the governance service returns review under a 0.10 threshold. The test still expects passing, which is the recorded unresolved mismatch.

## 13.11 Portfolio request

```python
class PortfolioAnalysisRequest(BaseModel):
    applications: list[PortfolioApplicationIn]
    group_key: str | None = None
    top_reason_count: int = Field(5, ge=1, le=10)
```

Each application includes the score request fields plus optional `actual_outcome`. When `group_key` exists in `sensitive_attributes` and an outcome is present, the handler contributes that row to fairness analysis. Rows without both values are still scored but excluded from fairness.

Production additions should include:

- Maximum request rows and bytes.
- Batch ID, cohort definition, product, policy, and model version.
- Per-row validation result and explicit partial-failure policy.
- Asynchronous job and result retrieval for large cohorts.
- Small-group suppression and authorized group dictionary.
- Immutable analysis manifest and downloadable signed report.

## 13.14 Audit list request

Query parameters:

| Parameter | Current handling | Notes |
|---|---|---|
| `limit` | bounded to 1 through 250 | default 100 |
| `offset` | bounded to zero or greater | offset pagination |
| `event_type` | exact string match | no enumeration at query schema |
| `application_id` | validated and tokenized before comparison | must be the caller's pseudonymous reference |
| `request_id` | exact string match | no tenant namespace |
| `model_version` | exact string match | no model-name filter |

Example:

```http
GET /v1/audit/events?limit=25&event_type=decision&application_id=app_example_001
```

The response includes a total count, effective limit and offset, and normalized events. The generated `id` is based on JSONL position and is not stable if the file is rewritten.

## 13.16 Error contract

FastAPI currently returns its standard detail shape for raised errors and Pydantic validation errors. Examples include:

```json
{"detail": "Unauthorized"}
```

```json
{"detail": "Missing required features: ['avg_daily_balance_6m']"}
```

Production errors need a stable public schema:

```json
{
  "error": {
    "code": "FEATURE_CONTRACT_INVALID",
    "message": "The submitted feature set is incompatible with the active contract.",
    "correlation_id": "opaque-correlation-reference",
    "field_errors": [
      {
        "field": "features.avg_daily_balance_6m",
        "code": "REQUIRED"
      }
    ],
    "retryable": false
  }
}
```

Internal model paths, stack traces, feature values, credential state, and cross-tenant detail must not appear.

## 13.18 SQLite schema

The principal implementation creates two tables:

```sql
CREATE TABLE IF NOT EXISTS decision_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT NOT NULL,
  application_id TEXT NOT NULL,
  request_id TEXT NOT NULL,
  model_name TEXT NOT NULL,
  model_version TEXT NOT NULL,
  decision TEXT NOT NULL,
  score REAL NOT NULL,
  decision_threshold REAL NOT NULL,
  reason_codes TEXT NOT NULL,
  features_hash TEXT,
  features_json TEXT,
  sensitive_json TEXT,
  extra_json TEXT
);

CREATE TABLE IF NOT EXISTS outcome_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT NOT NULL,
  application_id TEXT NOT NULL,
  outcome_type TEXT NOT NULL,
  outcome_value INTEGER NOT NULL,
  extra_json TEXT
);
```

The current schema has no unique constraint on request ID or outcome identity, no foreign key between outcomes and decisions, no tenant column, no event-integrity column, and no indexes. It is not the source for the principal read API.

## 13.20 Training-report schema

The main training pipeline writes:

```json
{
  "model_name": "sklearn_logreg_baseline",
  "model_version": "0.0.1",
  "feature_schema_hash": "a991402390c9a9aa",
  "metrics": {

```

The report does not contain row counts, label distribution, split hashes, seed, coefficients, convergence status, calibration, threshold results, subgroup metrics, package versions, artifact digest, or validation disposition. Those additions are mandatory for a governed model-development record.

## 13.21 Frontend data contracts

TypeScript types mirror principal API responses. This reduces accidental drift at compile time but does not validate runtime JSON. The live adapter casts returned JSON to the expected type:

```typescript
return (await res.json()) as T;
```

Production clients should validate runtime responses with generated OpenAPI clients or a runtime schema library. Contract tests should compare the TypeScript client schema with the backend OpenAPI document and reject breaking changes.

## 13.22 Contract-versioning rules

A change is breaking when it can alter parsing, vectorization, decision, explanation, audit linkage, or caller behavior. Examples include:

- Renaming a field.
- Changing required/optional status.
- Changing type, unit, range, precision, lookback, or missingness.
- Reordering model vector columns.
- Changing decision states or threshold inclusivity.
- Changing reason-code meaning.
- Removing response fields.
- Changing error codes or idempotency semantics.
- Changing event identity or join-key policy.

Recommended version headers and fields:

```text
API version: path major version
feature contract: immutable semantic version plus full-definition hash
model artifact: immutable model version plus digest
decision policy: separate immutable version
reason dictionary: separate immutable version
audit schema: immutable event-schema version
```

The response should echo every decision-relevant version.

## 13.23 Contract test matrix

| Test class | Minimum assertions |
|---|---|
| Required fields | Every required feature rejected when absent |
| Unknown fields | Unknown feature and top-level field policy exercised |
| Types | Strings, booleans, arrays, nulls, NaN, infinity, and integer/float boundaries |
| Ranges | Below, at, within, at maximum, and above every governed boundary |
| Optional values | Omitted, explicit null if permitted, zero, typical, maximum |
| Ordering | Vector order equals artifact order and schema hash |
| Version mismatch | Client feature version incompatible with artifact or policy |
| Authentication | Missing, incorrect, expired, wrong tenant, wrong scope |
| Idempotency | repeat same digest, repeat different digest, concurrent duplicate |
| Errors | stable code, safe message, correlation ID, no sensitive detail |
| Audit | one successful operation produces one linked event and stable read result |
| Serialization | OpenAPI examples, Python models, TypeScript types, and stored events agree |
